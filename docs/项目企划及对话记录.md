## 一、项目概述

### 1.1 目标

在 Minecraft Java 版中，寻找满足以下条件的种子：
- **搜索范围：** 以(0,0)为中心，(-200,-200) 到 (200,200) 的 401×401 区块网格
- **核心条件：** **5×5 区块窗口**（80×80 方块）内存在 **≥19 个史莱姆区块**（76%）
- **搜索空间：** 2^48 ≈ 281 万亿（2.8×10^14）个种子（Java 版种子空间为 64 位，但实际结构生成仅依赖低 48 位，高 16 位固定为 0 即可）

### 1.2 背景

> 史莱姆区块是 Minecraft 中特定区块会自然生成史莱姆的机制。寻找满足特定密度条件的种子对服务器建设、红石机械或趣味挑战具有重要意义。每区块独立判定，概率为 10%，5×5=25 区块期望值为 2.5 个，要求 ≥19 个（76% 以上），属于**极端稀有事件**。

## 二、核心算法原理

### 2.1 史莱姆区块判定算法

Java 版史莱姆区块判定基于**区块坐标**的随机数计算，源码来自 [Minecraft Wiki](https://minecraft.wiki/w/Slime#Slime_chunks)：

> ⚠️ **关键注意：** Java 的 `int` 是 32 位有符号整数，所有 `(int)` 运算会发生自动溢出截断（只保留低 32 位）。**这是最容易出错的地方！** 若用 64 位整数完整计算，结果完全不同。

```
输入：区块坐标 (chunkX, chunkZ)，worldSeed（64位）

处理：
  第一步：计算 Random 构造函数的种子（注意所有 int 运算都是 32 位溢出截断）
    int t1   = chunkX * chunkX * 0x4c1906;         // 32位int乘法，溢出自动截断
    int t2   = chunkX * 0x5ac0db;                   // 32位int乘法，溢出自动截断
    int t3_z = chunkZ * chunkZ;                      // 32位int乘法，溢出自动截断
    long t3  = (long)t3_z * 0x4307a7L;              // 截断后的32位值提升为long再乘
    int t4   = chunkZ * 0x5f24f;                     // 32位int乘法，溢出自动截断

    long seedForRandom = (worldSeed + t1 + t2 + t3 + t4) ^ 0x3ad8025fL;

  第二步：Java Random.setSeed() 内部逻辑
    seedForRandom = (seedForRandom ^ 0x5DEECE66DL) & ((1L << 48) - 1);

  第三步：Java Random.next(31) — 生成下一个随机数，取高31位
    seedForRandom = (seedForRandom * 0x5DEECE66DL + 0xBL) & ((1L << 48) - 1);
    int bits = (int)(seedForRandom >>> 17);          // 48 - 31 = 17

判定条件：bits % 10 == 0  → 是史莱姆区块（10% 概率）
```

**关键点：**
- ⚠️ **32位溢出截断是必须的：** `(long)` 全程64位计算会算出完全不同的结果
- ⚠️ **第③项是先截断再乘：** `(int)(chunkZ²) × 0x4307a7L`，不是 `(long)chunkZ² × 0x4307a7L`
- 史莱姆区块完全由种子决定，与结构生成无关
- 不同 MC 版本间算法可能有差异（需针对性实现）
- 低 48 位相同则史莱姆布局完全一致

## 三、验证算法优化

### 3.1 朴素验证的复杂度

对于每个种子：
- 区块总数：401 × 401 = 160,801 个
- 5×5 窗口数量：(401-4) × (401-4) = 157,609 个
- **朴素法：** 每个窗口检查 25 个区块 → **~4.1M 次操作/种子**
- 这意味着在 GPU 上即使每秒检查 1e6 种子，也需要 4.1e12 次操作，远超出 GPU 能力

### 3.2 二维前缀和优化（推荐方案）

**核心思路：** 预先计算整个 401×401 网格的前缀和数组，使任意 5×5 矩形区域的和可在 O(1) 时间内求出。

**步骤（对单个种子）：**
1. 构建布尔网格 slime[x][z]（x,z 从 -200 到 200 映射到 0..400）
2. 计算二维前缀和
3. 遍历所有 5×5 窗口，每个窗口 O(1) 查询

**复杂度：** 160k 次区块判断 + 160k 次前缀和计算 + 157k 次窗口查询 ≈ **320k 次/种子**

### 3.3 滑动窗口 + 行前缀和（GPU 适配版本）

**问题：** 完整 401×401 布尔网格约 160KB/线程，GPU 显存压力巨大。

**优化方案（逐行扫描 + 维护 5 行前缀和）：**
- 每个线程只维护两个数组：
  - `cur_prefix[402]`：当前行的前缀和
  - `window_rows[5][402]`：最近 5 行的每行前缀和（循环索引）
- 按行遍历 z 从 -200 到 200，实时构建前缀和
- 当积累 ≥5 行时，对每列计算 5 行窗口和
- **内存占用：** 仅 ~8,040 字节/线程（5 × 402 × 4字节）
- **复杂度不变：** ~320k 次操作/种子

### 3.4 提前终止优化
- 一旦发现某个窗口总和 ≥19，记录种子并提前结束
- 多个窗口可同时计算

## 五、GPU 实现方案

### 5.1 CUDA 内核设计

```
每个线程处理一个种子（或连续的一段）

线程布局：
  - gridDim × blockDim 个线程并行
  - 每个线程通过步长 gridDim × blockDim 遍历种子序列

内核伪代码：
  __global__ void search_kernel() {
      unsigned long long seed_start = ...;
      unsigned long long step = gridDim.x * blockDim.x;

      for (seed = seed_start + threadIdx.x + blockIdx.x * blockDim.x;
           seed < seed_end;
           seed += step) {

          int window_rows[5][402];  // 5 行前缀和
          int cur_prefix[402];

          for (int rz = 0; rz < 401; rz++) {
              // 计算当前行前缀和
              for (int cx = 0; cx <= 400; cx++) {
                  bool is_slime = isSlimeChunk(seed, cx - 200, rz - 200);
                  cur_prefix[cx+1] = cur_prefix[cx] + (is_slime ? 1 : 0);
              }
              // 存入循环缓冲区
              memcpy(window_rows[rz % 5], cur_prefix, 402 * sizeof(int));

              if (rz >= 4) {
                  // 检查所有 5x5 窗口
                  for (int cx = 0; cx <= 396; cx++) {
                      int sum = 0;
                      for (int r = 0; r < 5; r++) {
                          sum += window_rows[r][cx+5] - window_rows[r][cx];
                      }
                      if (sum >= 19) {
                          atomicAdd(&found_count, 1);
                          results[found_count-1] = seed;
                          return;
                      }
                  }
              }
          }
      }
  }
```

### 5.2 重要实现细节

- **种子生成：** 顺序枚举或随机抽样（xorshift64 PRNG）
- **提前退出：** 全局原子标志，所有线程定期检查
- **结果收集：** 原子计数器 + 全局数组
- **显存需求：** 极小（每个线程 ~8KB 局部内存）

## 七、不同 MC 版本算法差异

> 史莱姆区块生成算法在不同 Java 版中可能存在差异，需要在实现时针对目标版本做适配。

| MC 版本 | 算法变化 |
|:--------|:---------|
| 1.12- | 经典算法（同上） |
| 1.13-1.17 | 无变化 |
| 1.18+ | 世界生成大改，但史莱姆区块算法 **基本不变** |
| 1.19+ | 无变化 |
| 1.20+ | 无变化 |
| 1.21+ | 需确认 |

**建议：** 以目标版本的实际代码为准，可从 cubiomes 库中提取对应版本的算法。

## 八、可行性分析总结

| 维度 | 结论 |
|:----|:------|
| 🖥️ **硬件** | CMP 90HX 等 GPU 足够，显存需求极低 |
| ⏱️ **时间** | 月吞吐 ~71 亿种子，找到即停（期望时间取决于目标密度） |
| 🔧 **可行性** | 滑动窗口+前缀和优化成熟，CUDA 实现清晰 |
| 🎯 **成功率** | 2^48 空间中必定存在符合条件种子，但需要一定运气 |

### 优化建议

1. **多 GPU 并行：** 多个 GPU 分摊种子空间，线性加速
2. **早期终止：** 发现 → 停机，避免无效计算
3. **随机抽样：** 如果顺序枚举长时间无结果，可切换随机策略
4. **精度权衡：** 可先降低窗口大小（如 4×4）快速过滤，再精确验证
